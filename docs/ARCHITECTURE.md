# Архитектура

## Технологические решения

- React + TypeScript + Vite.
- React Context и `useReducer` вместо стороннего state manager.
- CSS Modules для изоляции стилей.
- Vitest и React Testing Library.
- LocalStorage как единственное постоянное хранилище.

## Предлагаемая структура

```text
src/
  app/                 композиция приложения, Provider и Error Boundary
  components/          переиспользуемые UI-компоненты
  features/
    dashboard/         сводка и приоритеты
    portals/           список и карточка
    event-log/         журнал событий
    ai-worklog/        встроенный AI Worklog
  domain/              типы, расчёт риска, рекомендации и проверки действий
  data/                демоданные и версия схемы
  persistence/         чтение, валидация и запись LocalStorage
  styles/              глобальные токены и базовые стили
  test/                общая настройка тестов
```

Создавать директории следует по мере появления реального кода, не заранее.

## Управление состоянием

`PortalProvider` владеет единым `AppState`:

```text
AppState
├── worlds
├── portals
├── events
├── selectedPortalId
├── activeView
├── filters
└── notification/error
```

Компоненты отправляют типизированные действия в reducer. Reducer вызывает или
использует результат чистых доменных функций, но не обращается к LocalStorage.
Сохранение выполняется отдельным адаптером и эффектом Provider.

## Доменная модель

`World` и `Portal` — отдельные сущности. `Portal.destinationWorldId` ссылается
на `World.id`; количество существ получается селектором из мира и не хранится в
портале. Генератор порталов принимает источник случайности как зависимость,
чтобы тесты оставались детерминированными. Генератор не создаёт новый портал,
если уже существует 20 порталов со статусом, отличным от `closed`.

Минимальные доменные данные портала:

```text
Portal
├── id, name, destinationWorldId
├── energy                  // 0..100
├── dissipationCoefficient  // 0..1
├── stability               // 0..1
├── stabilizationBonus      // 0..0.75
├── initialLifetimeSeconds
├── wasCritical
├── observerAssigned
└── status                   // stable | dangerous | critical | closed
```

Время, случайность и период обновления внедряются в доменный сервис. Компоненты
не запускают собственные расчёты и не мутируют параметры портала.

## Расчёт времени и риска

Чистые функции в `src/domain/` реализуют:

```text
K = D * (1 - S)
T_remaining = C * E / K
R = clamp(1 - T_remaining / T_initial, 0, 1)
```

`E = 0` даёт `T_remaining = 0` и `R = 1`. `K = 0` обрабатывается без деления на
ноль: `T_remaining = Infinity`, `R = 0`. Для хранения в LocalStorage
бесконечность не сериализуется; адаптер хранит физические параметры, а время и
риск рассчитывает после загрузки.

Статус выводится из риска по границам `[0, 0.5)`, `[0.5, 0.8)` и `[0.8, 1]`.
Исключение — сохранённый `closed`. При достижении критичного диапазона
устанавливается `wasCritical`; если после этого селектор количества существ
возвращает 0, выполняется необратимый переход в `closed`.

Периодическое изменение коэффициентов может менять оценку оставшегося времени
и риск в обе стороны. До реализации нужно отдельно утвердить `C`, длительность
периода, закон расходования энергии, инициализацию `T_initial` при `K = 0` и
состояние после `T_remaining = 0`.

## Действия первой версии

Чистые селекторы определяют важность относительно всех незакрытых порталов в
тот же мир:

```text
important = creatures > 0 &&
  (activeToWorld.length == 1 ||
   activeToWorld.every(status is dangerous or critical))

veryImportant = creatures > 0 && activeToWorld.length == 1
```

`stabilize` доступен важному порталу со статусом `dangerous` или `critical`,
если `stabilizationBonus < 0.75`.
Reducer хранит временные метки не более чем трёх последних попыток внутри
скользящего окна 60 минут. Проверка лимита и запись попытки используют
внедряемые часы. Проверка доступности выполняется до расходования попытки.

Вероятность и результат рассчитываются чистой функцией с внедряемым источником
случайности:

```text
P = clamp(0.90 - 0.65 * risk + 0.15 * observer, 0.20, 0.80)
A = 0.08 + 0.17 * random()
B_new = min(0.75, 1 - (1 - B_old) * (1 - A))
S_effective = S + (1 - S) * B_new
K_effective = D * (1 - S_effective)
```

Первое случайное значение определяет успех, второе — силу только успешного
эффекта. Неудача сохраняет физические параметры, но расходует попытку.
Наблюдатель применяется к следующей допустимой попытке и затем снимается.
Предлагается не более одного `observerAssigned` во всём `AppState`.

`sendObserver` сначала проверяет статус: допустим только `dangerous`.
`critical`, `stable` и `closed` возвращают доменный отказ до любых остальных
проверок и ничего не меняют. Затем проверяются `veryImportant` и доступность
наблюдателя. При переходе портала с назначенным наблюдателем в `critical`
reducer атомарно снимает назначение. Поэтому в формуле для критичного портала
`observer` всегда равен 0.

Для проверки инварианта сравниваются оценки времени до и после действия на
одной временной отметке. Изменение времени между отметками относится к обычной
эволюции портала, а не к стабилизации.

Эффекты ручного `close` и `markQuestionable` всё ещё требуют согласования.
События попыток, назначения наблюдателя, изменения статуса и автоматического
закрытия записываются в журнал.

## Надёжность и доступность

- Кнопка должна иметь текст, а уровень риска — не кодироваться только цветом.
- Диалог подтверждения должен работать с клавиатуры и возвращать фокус.
- Ошибка загрузки LocalStorage восстанавливается через демоданные.
- Глобальный Error Boundary показывает понятный fallback.
- Все даты форматируются единообразно для русской локали.
